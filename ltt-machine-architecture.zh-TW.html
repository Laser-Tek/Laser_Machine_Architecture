第 1 部分

概觀

四個層是什麼，以及它們彼此如何相依。

1.1各層

共有四個層，相依性只能向下。組合根是唯一認識所有層的程式碼，並由它決定每個介面背後使用哪一個實作。

1.2職責

每一種類別只有一項工作。做了「絕不」欄中事情的類別，就是放錯了層。

角色所屬層負責絕不
檢視檢視版面配置、繫結、焦點；放置操作員必須使用的廠商畫面邏輯、硬體呼叫、建立服務
檢視模型檢視模型畫面狀態、命令，以及透過 Loc 取得的顯示文字參考 WinForms 或 WPF、阻塞、手動封送
作業Core一段機台流程：非同步且可取消。透過 IOperatorPrompt 詢問操作員操作控制項、顯示對話方塊、選擇執行緒
機台模型Core具名的軸、訊號與工站；安全政策參考廠商型別
狀態機Core管理一個生命週期，並拒絕無效的轉換呼叫裝置、進行 I/O、被兩個執行緒寫入
合約Platform某一類裝置的廠商中立介面含有廠商型別或已翻譯的文字
驅動程式驅動程式與一個 SDK 或通訊協定溝通。擁有自己的執行緒。擲回 HardwareException含有製程規則、顯示對話方塊、使用 Loc
模擬器驅動程式依據共用的 SimWorld 實作合約含有製程規則
組合根檢視（主程式）選擇實作、將它們串接起來、執行啟動與關閉程序其他任何事

1.3組件與相依性

組件所屬層可以參考絕不參考

第 2 部分

各層

從畫面到硬體，各層的職責、內容與規則，以及把它們串接起來的組合根。

2.1檢視

檢視層分為兩部分。

組件內容
<Machine>.exe主應用程式：本機台的表單與使用者控制項、組合根，以及下層所需埠（port）的 WinForms 實作（對話方塊服務、操作員提示、檔案對話方塊、日誌面板）。操作員必須使用的廠商畫面也由它放置，例如 AISYS VAlign 的教導畫面。
LTT.UI.WinForms所有機台共用、不認識任何機台的 UI 工具組：
  • LocUi（依語言設定字型與文字）。
  • Bind(ICommand) 輔助方法。
  • JogPad，以及 I/O、相機參數與光源的裝置面板。每個面板都針對裝置合約運作，標籤文字由呼叫端提供。
LTT.UI.Wpf 將是它的 WPF 對應版本。
  • 一個檢視只繫結到一個檢視模型，繫結集中寫在建構函式中的一個區塊，除此之外不含任何邏輯。
  • 頁面由容器建立，並以程式碼加入主視窗，因此可以接受建構函式參數。每個頁面自己的設計工具仍可正常使用。
  • 第二台機台可以原封不動重用的任何東西，都放進 LTT.UI.WinForms，而不是放在機台的 exe 中。
  • 文字來自字串表的鍵值，字型來自 LocUi.ApplyFontTree。檢視從不設定字面文字或字型。

2.2檢視模型

MVP 與 MVVM 都能把畫面邏輯與控制項分開。差別在於轉換到 WPF 時，哪些部分能保留下來：

MVP（被動檢視）

  • Presenter 透過 IProductionView 介面呼叫 view.SetBlockText(…)。
  • 每個畫面都需要這個介面、一個 presenter，以及在 code-behind 中手寫的實作。
  • WPF 與這種風格相抵觸。每個 WPF 畫面都需要一個轉接器，把 presenter 的呼叫轉成可繫結的屬性。

MVVM（採用）

  • 檢視模型公開屬性與命令，並引發 PropertyChanged。它對檢視一無所知。
  • .NET Framework 上的 WinForms 原生支援屬性繫結。命令只需要一個小型輔助方法。
  • WPF 不需修改即可繫結同一個類別，因此轉換到 WPF 只需要撰寫新的檢視。

LTT.<Machine>.Presentation / Production / ProductionViewModel.cs

internal sealed class ProductionViewModel : ViewModelBase
{
    private readonly IProductionRun _run;
    private string _blockText = "";

    public ProductionViewModel(IProductionRun run, IMachineState state, IEventBus events)
    {
        _run = run;
        StartCommand = new AsyncCommand(ct => _run.RunAsync(ct), () => state.Mode == MachineMode.Idle);
        StopCommand  = new RelayCommand(_run.Stop, () => state.Mode == MachineMode.Running || state.Mode == MachineMode.Paused);
        events.Subscribe<RunProgress>(OnProgress);              // 在 UI 執行緒上傳遞
        events.Subscribe<MachineStateChanged>(_ => RaiseCanExecuteChanged());
    }

    public AsyncCommand StartCommand { get; }
    public RelayCommand StopCommand { get; }
    public string BlockText { get => _blockText; private set => Set(ref _blockText, value); }

    private void OnProgress(RunProgress e) => BlockText = Loc.Format("Run.Block", e.Index + 1, e.Total);
}
  • 天生與 UI 無關。ICommand 與 INotifyPropertyChanged 位於基礎類別庫中。ViewModelBase、AsyncCommand 與 RelayCommand 來自 LTT.Platform。
  • 只有一個地方把點擊轉成 await。AsyncCommand 在執行期間會停用自己，並記錄任何例外。前端其他地方都沒有 async void。
  • 只保存畫面狀態。檢視模型只保存它的畫面要顯示與編輯的內容。關於機台的事實來自 Core，透過 MachineState、讀取模型與匯流排取得。
  • 其他視窗透過一個泛型的 IDialogService.ShowAsync<TViewModel>() 開啟，它會找出為該檢視模型註冊的檢視。不會有「每個視窗一個方法」的啟動器。
  • 保持精簡。相依項超過大約八個的檢視模型，就是在做作業的工作，這些邏輯應移到 Core。防護機制 G5 會檢查這一點。
  • 從第一次提交就開始測試，透過機台測試夾具在模擬器上執行，並搭配腳本化的對話方塊服務。

2.3Core：機台與作業

Core 包含機台所做的一切，不含 UI，也不含廠商程式碼。它是無介面（headless）的：WinForms、WPF、測試夾具，或 MES 連線、維護工具等遠端介面，都以相同方式透過作業來驅動它。

區域內容範例
機台模型建構在裝置合約之上的具名軸、訊號與工站，加上安全政策Stage（XY）、Z 軸與 θ 軸、具有具名輸入與輸出的 MachineIo、VisionStation、MotionSafetyPolicy
作業每段機台流程一個類別初始化、產品上料、對位、生產運行、振鏡網格校正、相機–雷射偏移、尋焦、功率校正、手動運動
狀態生命週期與警報MachineState、ProductionRun、AlarmService
儲存Core 所擁有資料的埠，以及它們的檔案實作IProductRepository、ICalibrationStore、IProductionRecordSink、ISettingsStore
主程式埠Core 需要應用程式提供的東西IOperatorPrompt、ILogger<T>、IEventBus、TimeProvider

作業

  • 作業是 async Task，並接受 CancellationToken。它透過 MachineOperations 執行；MachineOperations 讓作業獨占它所指名的資源、設定機台狀態，並掌管取消。
  • 作業使用機台模型，而只有機台模型使用裝置合約。共用步驟，例如在安全高度移動或尋找標記，屬於機台模型，絕不在作業之間複製。
  • 作業透過事件回報進度，並透過 IOperatorPrompt 詢問操作員。它們從不顯示 UI。
  • 參數以不可變快照的形式傳入。一次運行在開始時讀取一次產品與設定，運行期間所做的編輯不會影響它。

運動安全政策

MotionSafetyPolicy 保存每次移動都必須通過的規則：軟體極限、長距離 XY 移動前 Z 軸須位於安全高度、互鎖已閉合，以及機台不在 Alarm 狀態。機台模型會執行政策要求的動作，例如抬升 Z 軸；其他情況則以指明違反規則的 HardwareException 拒絕。命令的 CanExecute 會詢問同一個政策，因此按鈕被停用的原因，與移動會被拒絕的原因相同。

資源

MachineOperations 分配具名資源：載台、雷射、相機或整個工站。單工站機台以一個資源代表整台機台。有兩個工作台或兩個加工頭的機台，則每個工站宣告一個資源，如此兩個作業就能同時執行，而不需要重新設計。

2.4Platform

LTT.Platform 由所有機台共用。它包含使用裝置時所透過的合約，以及其他層賴以建構的小型基礎核心。它不參考任何 UI 框架；共用的 UI 工具組屬於檢視層。

區域內容
裝置合約IDevice、IMotionController / IAxis、IDigitalIO、ICamera、IMarkFinder、ILaserSource / ILaserPresets、IMarkingEngine、ILightController、IDistanceSensor
能力介面選用的廠商功能，以 as 探索：IAnalogInputs、ICommandScriptChannel
裝置執行緒DeviceGate、DeviceWorker，以及供 UI 綁定型裝置使用的 UI 執行緒呼叫器；它建構在 SynchronizationContext 之上，因此不需要任何 UI 框架（見「驅動程式」）
錯誤HardwareException、HardwareErrorCode
基礎核心IEventBus、ViewModelBase、AsyncCommand、RelayCommand、IDialogService、IOperatorPrompt、MachineOperations 背後的作業執行器
在地化Loc、字串表、languages.tsv

合約規則

  • 合約與廠商無關。其中不含廠商型別，也不含已翻譯的文字。
  • 每個長時間作業都是非同步的，並接受 CancellationToken。取消時先停止硬體，再擲回 OperationCanceledException。
  • 事件在驅動程式的執行緒上引發。使用端透過匯流排接收事件。
  • 狀態是不可變快照（例如 AxisStatus），以原子方式整個替換，因此讀取端絕不會看到只更新一半的資料。
  • 廠商的額外功能做成能力介面，而不是做成讓其他所有驅動程式都得寫空實作的成員。
  • 在同一主版本內，變更只能是新增。移除或修改成員意味著 Platform 的新主版本（見維護）。

2.5驅動程式與模擬

每個裝置都遵循相同的結構。Core 呼叫廠商中立的合約。合約背後的驅動程式決定由哪個執行緒呼叫 SDK，並把 SDK 錯誤轉成單一例外型別。位於同一合約背後的模擬器，則讀寫一個共用的模擬機台。

四種執行緒模型

每個驅動程式在其類別註解（remarks）中聲明自己的執行緒模型。需要機制的模型，在 Platform 中都有對應的機制。

模型機制適用情況範例
UI 綁定型UI 呼叫器操作員必須使用廠商自己的畫面，因此其控制項顯示在主視窗中使用教導畫面與影像顯示時的 AISYS VAlign。適用規則 T8
擁有者執行緒DeviceWorker綁定在建立它之執行緒上的 SDK：STA COM 物件、不需要其畫面的 ActiveX 控制項（裝載於隱藏視窗）、具執行緒親和性的原生函式庫MarkingMate 控制項、ACS SPiiPlus 等 COM 運動通道、USB 修調引擎函式庫
序列化DeviceGate請求／回應式通訊協定，以及非執行緒安全、但可從任意執行緒呼叫的 SDKLumentum 雷射、RS-232 光源控制器、TCP 高度感測器、Googol GTS I/O
自由執行緒無具有自己回呼執行緒的執行緒安全 SDKAerotech A3200（在背景工作中執行阻塞式移動，狀態來自診斷回呼）、Basler pylon

依據 SDK 手冊中的執行緒安全說明來指定模型，而不是依據「剛好能動」的結果。

ActiveX 裝置

MarkingMate 與 AISYS 都以 ActiveX 形式提供開發者介面。

  • MarkingMate：擁有超過 1,000 個函式的 OCX，是 Eastern Logic 提供的整合途徑。除了 I/O 訊號與選用的 TCP/IP 文字輸入之外，使用手冊未列出其他 API。
  • AISYS：VAlign 與其底層的 OVK Framework 都是 ActiveX 元件。VAlign 以完整視覺系統的形式販售，附有自己的操作畫面。它唯一的其他介面是 RS-232 命令，供 PLC 控制的機台使用。

ActiveX 控制項需要三樣東西：單執行緒單元（STA）執行緒、訊息迴圈，以及父視窗。它不需要可見，也不需要應用程式的主 UI 執行緒。因此有兩種裝載方式：

裝載方式做法時機
擁有者執行緒（建議）STA 模式的 DeviceWorker 執行自己的訊息迴圈，並把控制項裝載在隱藏表單上。所有呼叫都經由此 worker。操作員不需要廠商畫面時，例如 MarkingMate 打標。如需打標檔預覽，由我們自己的檢視根據文件繪製。
UI 綁定型控制項放在主視窗的面板中，呼叫會 Post 到 UI 執行緒的 SynchronizationContext。操作員使用廠商畫面時，例如 VAlign 教導畫面。適用規則 T8。
  • 為何建議擁有者執行緒。裝置不再與 UI 共用執行緒，因此忙碌的畫面不會延誤打標，長時間的裝置呼叫也不會凍結畫面。對該裝置而言，規則 T8 所述的重入風險也隨之消失。
  • 先向廠商確認。把控制項移到擁有者執行緒之前，先向廠商確認驅動程式使用的每個控制項都能在隱藏視窗上運作，然後在機台上執行該裝置的合約測試。已有數個 MarkingMate 控制項在隱藏狀態下使用。OVK 處理模組能否在沒有視窗的情況下運作，目前沒有公開文件說明。
  • UI 綁定的情況可以避免。OVK Framework 也提供圖樣比對與對位的處理模組（OvkPat、OvkAlign），且 AISYS 列出支援 .NET Framework 與 .NET 5/6。以這些模組建構的驅動程式可以在沒有廠商畫面的情況下尋找標記，教導則在我們自己的檢視中完成。由於 IMarkFinder 與廠商無關，也可以換用其他視覺函式庫而不必修改 Core。
  • 驅動程式中不含 UI 工具組。裝載 ActiveX 控制項需要在驅動程式內使用 System.Windows.Forms，以取得 AxHost。驅動程式從不參考 LTT.UI.*。它透過 IHasHardwareView 把廠商畫面交給檢視層，由檢視層決定要放在哪裡。
// LTT.Platform：一次一個呼叫。逾時會轉成 HardwareException(Timeout, device)。
public sealed class DeviceGate
{
    public DeviceGate(string device, TimeSpan timeout);
    public Task<T> RunAsync<T>(Func<CancellationToken, Task<T>> call, CancellationToken ct);
}

// LTT.Platform：每個呼叫都在建立 SDK 物件的執行緒上執行（STA 會處理訊息）。
public sealed class DeviceWorker : IDisposable
{
    public DeviceWorker(string device, ApartmentState apartment);
    public Task<T> RunAsync<T>(Func<T> call, CancellationToken ct);
}

先啟動，再等待。長時間作業（移動、原點復歸、打標）以一個短呼叫開始，然後 await 完成事件或狀態。它們絕不會是 gate 或 worker 上的一個長時間阻塞呼叫，因此 Stop 永遠送得進去。

驅動程式規則

  • 每個廠商 SDK 一個組件。它參考該 SDK，並把 SDK 的原生 DLL 帶入建置輸出。機台只參考它實際具備之硬體的驅動程式。
  • LTT 自行透過序列埠或 TCP 撰寫、不使用廠商 SDK 的驅動程式，共用 LTT.Hardware.Protocols。
  • 每個驅動程式都附有自己的註冊輔助方法，例如 AddA3200Motion(axes)。
  • 驅動程式把每個 SDK 錯誤轉成 HardwareException，廠商狀態碼只留在自己內部，且不含任何製程規則。
  • 實體驅動程式在標有 [MethodImpl(MethodImplOptions.NoInlining)] 的工廠方法中建立，因此模擬時絕不會載入廠商組件。
  • IDevice 有一個 State（Disconnected、Connecting、Ready 或 Faulted）。狀態變更以 DeviceStateChanged 發布到匯流排上，啟動畫面與狀態列都會顯示。

模擬

  • 每個合約都有模擬器。每個裝置在 Hardware.ini 中設為 Real 或 Simulated，而 --simulate 會讓所有裝置都改為模擬，因此應用程式可以在未安裝任何廠商 SDK 的筆電上執行。
  • 通訊協定驅動程式以真正的程式碼對裝置仿真器執行；Lumentum 仿真器就是其中之一。只有傳輸線路是模擬的。
  • SimWorld 保存模擬的機台：
    • 載台位置，由運動模擬器寫入。
    • 輸出，以及由輸出推導出的輸入（開啟真空後，真空感測器會在一段延遲後觸發）。
    • 雷射狀態，並據此提供功率計讀值。
    • 已載入產品的標記位置。
    • 故障注入，例如在指定時間打開門。
    機台提供一個 SimWorldProfile，說明哪個輸出驅動哪個輸入。
  • 若實體雷射或打標引擎搭配模擬的運動或 I/O，啟動程序會拒絕執行。模擬模式會在標題列顯示橫幅，Release 建置則需要加上 --allow-simulation。

3.1執行緒

執行緒有三種，每種都屬於一個層。UI 執行緒屬於檢視與檢視模型。Core 在執行緒集區上執行，不在乎是哪一條。裝置執行緒屬於各自的驅動程式。

顯示給操作員的廠商 ActiveX 控制項（例如 AISYS VAlign）位於 UI 執行緒上，其驅動程式會把每個呼叫封送到那裡。這使得阻塞 UI 執行緒不只是慢，更是危險：等待封送到已被阻塞之 UI 執行緒的驅動程式會發生死結。盡可能把 ActiveX 裝置裝載在自己的擁有者執行緒上（見驅動程式），可讓這種情況很少發生。

執行緒規則

  1. UI 執行緒從不等待。檢視與檢視模型不使用 .Wait()、.Result、Thread.Sleep、Application.DoEvents 或同步的 Invoke。 分析器會在建置時強制執行（G3）。
  2. 檢視模型的屬性只在 UI 執行緒上變更。匯流排在那裡傳遞事件，檢視模型中 await 之後的程式碼也會在那裡繼續執行。 因此檢視模型從不使用 ConfigureAwait(false)。若 PropertyChanged 在其他執行緒上引發，WinForms 繫結會擲回例外。
  3. Core 與驅動程式使用 ConfigureAwait(false)，且從不封送。每個長時間作業都是 async Task，並接受 CancellationToken。檢視層以下沒有 async void。
  4. 取消只有一個擁有者。MachineOperations 執行作業並掌管其取消。Stop 會取消目前的作業，致命警報也會。 檢視與檢視模型不持有 CancellationTokenSource 欄位。
  5. 驅動程式擁有自己的執行緒。每個驅動程式宣告四種執行緒模型之一，並使用對應的 Platform 機制。阻塞式 SDK 呼叫留在驅動程式內部。 驅動程式之上的程式碼呼叫它時，從不需要 Task.Run。
  6. 連續狀態用拉取，離散事件用推送。軸位置與 I/O 電位是快照，由 UI 計時器每秒讀取 10–20 次。警報、互鎖、進度與狀態變更則走匯流排。 這讓高頻率資料不會進入匯流排。對指示燈而言，每次輪詢合併成一次更新就足夠了。
  7. 操作員提示是非同步的。IOperatorPrompt.AskYesNoAsync(…) 傳回 Task<bool>。主程式 Post 到 UI 執行緒，顯示一個由主視窗擁有的對話方塊，Core 則 await 答案。
  8. UI 執行緒在處理訊息期間所執行的程式碼中，不呼叫裝置。Paint、計時器與裝置事件處理常式讀取快取的快照，從不呼叫裝置。 呼叫 UI 綁定型 ActiveX 控制項，或進行任何 STA COM 呼叫時，等待期間都會處理訊息。佇列中的 paint 或計時器事件可能因此在呼叫中途執行，並再次呼叫同一個裝置。這種重入會使裝置停滯，或破壞其狀態。

事件規則

  1. 只有一種機制。Core 型別不向其他層公開 C# 事件，也不實作 INotifyPropertyChanged。只有檢視模型會實作。 唯一的例外是 Loc.LanguageChanged，它是在地化引擎的一部分。
  2. 每次更新只封送一次。匯流排 Post 一次，檢視模型在處理常式中直接設定屬性。
  3. 事實由其擁有者發布。只有事實的擁有者會發布它。事件是過去式的事實，絕不是請求，也絕不是 UI 手勢。
  4. 處理常式之間沒有順序。如果 B 必須在 A 之後執行，就由 A 的擁有者直接呼叫 B，或讓 B 監聽 A 所發布的事件。
  5. 沒有無人訂閱的事件。有一個測試會列出沒有訂閱者的事件型別。擲回例外的處理常式會被記錄，其他處理常式仍會執行。

機台狀態

Core 中的 MachineState 擁有機台的模式，以及模式之間允許的轉換。每個命令的 CanExecute 都會讀取模式，並與安全政策一起決定操作員在任何時刻能做什麼。

運行也有自己的狀態機

ProductionRun 保存一次運行的生命週期：Ready、Aligning、Marking（第 i／n 區塊）、Finishing，最後是 Completed、Cancelled 或 Failed。暫停是運行在其檢查點上 await 的一道閘門。此類別發布 RunProgress 與 RunCompleted。它是 Core 中的一般類別，具有受保護的狀態轉換、一個鎖與一個寫入者（運行作業），並經過單元測試。要詢問運行是否進行中，只能問這一個地方。沒有另外的「processing」或「marking」旗標。

安全狀態

每台機台在 Core 中定義一個 SafeState 程序：停止運動、關閉雷射出光並關閉光閘、停止打標，並把輸出設為安全值。它在致命警報、緊急停止、未處理例外與關閉時執行。每個步驟各自獨立嘗試，因此即使某個裝置已故障，程序仍會盡可能完成其餘步驟。有一個序列測試涵蓋此程序。

3.4資料與組態

機台讀寫的所有資料都位於單一資料根目錄下，與程式資料夾分開。資料存放在檔案中，絕不存放在登錄檔，因此複製資料根目錄即可備份或複製一台機台。程式資料夾在每次部署時都會被替換，並視為唯讀。

日誌規則

  1. 結構化訊息。透過 ILogger<T> 以訊息範本與具名屬性記錄，例如 _log.LogInformation("Moved {Axis} to {Position} mm", axis, pos)，絕不使用字串內插。 這些值會保持為可搜尋的欄位。分析器 CA2254 會把非常數範本視為建置錯誤。
  2. 每個作業的開始與結束只記錄一次，而且只在一個地方記錄。MachineOperations 在開始時記錄名稱、參數與配方檢查碼，在結束時記錄結果與耗時。個別作業不重複記錄。
  3. 每次狀態轉換與警報變更都會記錄。包括機台模式、運行狀態，以及每次警報的引發、清除與確認，並附上 id 與使用者。
  4. 裝置失敗會帶有其上下文。包括裝置、命令、廠商錯誤碼，以及以 SDK 例外作為內部例外的 HardwareException。成功的裝置通訊只在 Verbose 層級記錄。
  5. 例外只記錄一次：在處理它的地方，並附上例外物件。使用 _log.LogError(ex, …)，絕不使用 ex.Message。中間的層不做「記錄後再擲回」。 這樣一個例外只會產生一筆含完整堆疊的 Error 項目，而不是五份不完整的副本。
  6. 不可無聲地 catch。每個 catch 只能做三件事之一：重新擲回；處理問題並記錄 Warning；或把例外轉成以原始例外為內部例外的 HardwareException。有一個原始碼掃描測試會找出空的 catch 區塊。
  7. 操作員的決定都有紀錄。每個提示及其回答都會記錄，例如「操作員確認在門開啟的情況下啟動」。
  8. 確切知道執行了什麼。載入組態、配方或校正資料時，會記錄檔案、其結構描述版本，以及簡短的 SHA-256 檢查碼。生產紀錄也會儲存配方檢查碼。
  9. 不含機密。密碼絕不出現在任何日誌中，個人資料只以登入名稱的形式出現。
  10. 日誌記錄絕不讓機台停下。輸出端（sink）都是非同步的；失敗的輸出端會被回報，但絕不會阻塞機台程式碼，也不會向其擲回例外。

儲存與保存

  • 同一批事件的兩種格式。文字檔（diagnostic-yyyyMMdd.log）供人閱讀。精簡 JSON 檔（.clef）供 Seq、jq 或試算表匯入等工具使用。每天或檔案達到 200 MB 時會開始一個新檔案。
  • 保存期限：
    • 診斷日誌：180 天；
    • 當機報告與傾印檔：一年；
    • 稽核日誌、警報歷程與生產紀錄：應用程式絕不刪除。
  • 時間戳記使用本地時間，包含毫秒與 UTC 偏移。機台時鐘在裝機調試時設定 NTP 同步，因此機台、MES 與其他設備的日誌可以對齊。
  • 磁碟空間在啟動時及每小時檢查一次。低於門檻時會引發 Warning 警報，因此日誌絕不會在無人察覺的情況下塞滿資料磁碟。
  • 支援資料包：一個命令即可把近期日誌、當機報告、稽核日誌、警報歷程、組態與版本資訊壓縮成 zip 檔。

3.6例外、當機與無回應

每一次失敗，無論是否被處理，都必須留下完整的堆疊追蹤，以及足夠的上下文，讓人不必在機台上重現就能解釋原因。

保留堆疊追蹤

  • 隨附 PDB 檔。Release 建置產生可攜式 PDB（<DebugType>portable</DebugType>），並部署在每個組件旁邊。堆疊追蹤因此包含檔名與行號；.NET Framework 從 4.7.2 版起可為此讀取可攜式 PDB。
  • 正確地重新擲回。使用 throw;，絕不使用會丟棄原始堆疊的 throw ex;。包裝例外時，把原始例外作為 InnerException 傳入。要在另一個執行緒上重新擲回，使用 ExceptionDispatchInfo.Capture(ex).Throw()。
  • 保留廠商的細節。驅動程式把 SDK 錯誤轉成帶有裝置、命令與廠商錯誤碼的 HardwareException，並以 SDK 例外作為內部例外，讓廠商自己的訊息與堆疊得以保留。
  • 例外變成欄位。Serilog.Exceptions 會把例外屬性、內部例外與 AggregateException 的子例外寫成結構化欄位，使其在 .clef 日誌中可以搜尋。

未處理的例外

  1. 最先安裝處理常式，在 Program.Main 中、建置容器之前：AppDomain.UnhandledException、Application.ThreadException 與 TaskScheduler.UnobservedTaskException。
  2. 以 Fatal 層級記錄完整的例外。
  3. 寫入當機報告至 Logs\Crash\crash-yyyyMMdd-HHmmss.txt。內容包括：
    • 含完整堆疊的例外；
    • SessionId，以及目前的 OperationId 與 RunId；
    • 機台與運行狀態；
    • 應用程式、驅動程式與 SDK 版本，以及硬體設定檔；
    • 環形緩衝區中所有層級的最近 2,000 筆日誌事件。
  4. 執行安全狀態，然後排清日誌（Log.CloseAndFlush()）。
  5. 通知操作員並關閉。操作員會看到一則附有當機報告參考編號的訊息。接著應用程式關閉，因為未處理的例外會讓它處於未知狀態。下一次啟動畫面會顯示上一次當機的參考編號。

原生當機與無回應

  • 為廠商 DLL 產生傾印檔。原生廠商程式碼內的當機（存取違規）可能在任何 .NET 處理常式執行之前就結束處理程序。因此，裝機調試時會為應用程式開啟 Windows 錯誤報告的本機傾印：HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\<Machine>.exe，並將 DumpFolder 設為 <data root>\Logs\Dumps、DumpType=2（完整傾印）、DumpCount=5。傾印檔可以搭配 PDB 在 Visual Studio 或 WinDbg 中開啟。
  • UI 看門狗。一個背景計時器每秒 Post 一次心跳到 UI 執行緒。若心跳等待超過 5 秒，看門狗會記錄一筆 Warning，指出目前的作業與最後一次裝置呼叫。超過 30 秒時，它會把處理程序傾印（MiniDumpWriteDump）寫入 Logs\Dumps，從中可以看出每條執行緒卡在哪裡。
  • 緩慢的裝置呼叫。當呼叫時間超過預期時，DeviceGate 與 DeviceWorker 會記錄一筆 Warning，指出裝置與命令。卡住的 SDK 呼叫在演變成無回應之前就會被發現。

驗證可追溯性

  • 一個使用記錄型記錄器的序列測試，檢查每個作業都以其 OperationId 記錄開始與結束。
  • 一個故障注入測試讓模擬驅動程式擲回例外，接著檢查是否剛好有一行含例外與堆疊的 Error、一個 OperationId 相同的警報，以及一筆帶有 RunId 的 NG 紀錄。
  • 一個測試引發未處理的例外，並檢查當機報告已寫入、安全狀態已執行。
  • 防護機制：CA2254 是建置錯誤，原始碼掃描遇到空的 catch 區塊與 throw ex; 時會失敗。
第 4 部分

品質

架構在變動中如何保持正確：測試、自動檢查與維護規則。

4.1測試

各層的設計讓幾乎所有東西都能在沒有機台的情況下測試。測試分為三種。

種類涵蓋範圍執行時機
單元隔離測試單一類別：狀態機、政策、計算、檢視模型，以及針對裝置仿真器的驅動程式通訊協定編碼每次建置
裝置合約每個裝置合約一套共用測試，分別對模擬器與實體驅動程式執行模擬器：每次建置。實體驅動程式：在機台上
序列透過機台測試夾具在模擬器上執行完整作業。對於生產路徑的變更，運行產生的生產紀錄必須與前一版建置的相符每次建置

架構檢查（相依性、執行緒分析器、棘輪）請見 4.2 防護機制。在機台上，先執行裝置合約測試，再執行裝機調試檢查表。

裝置合約測試讓模擬器保持誠實

每個合約有一個抽象測試類別，說明每個實作都必須做到什麼。模擬器的子類別在每次建置時執行，實體驅動程式的子類別在機台上執行。如此一來，偏離實體裝置行為的模擬器會讓測試失敗，而不是讓序列測試因為錯誤的理由通過。

虛擬時間

延遲、逾時、輪詢間隔與模擬運動都從 TimeProvider 讀取時間。在 .NET Framework 上它來自 Microsoft.Bcl.TimeProvider 套件；.NET 8 則已內建。測試使用 FakeTimeProvider 明確地推進時間。這樣一次完整的生產運行在測試中只需幾秒，而且每次都以相同方式執行。檢視層以下沒有任何程式碼直接呼叫 Thread.Sleep 或 DateTime.Now。

機台測試夾具

一個測試輔助類別在模擬器之上建立真正的 Core 服務。它使用暫存的資料根目錄、記錄型記錄器與腳本化的操作員提示，並以與組合根相同的 Add…() 輔助方法串接。序列測試與檢視模型測試共用它。

4.2防護機制

規則只有在「違反它就會讓建置失敗」時才守得住。以下檢查可防止架構逐漸腐化。

  1. 用測試，不用腳本。每項檢查都是在一般建置中執行的 MSTest 測試或分析器。
  2. 不可空洞地通過。每個原始碼掃描都會斷言自己有找到檔案。掃描到零個檔案即視為失敗。
  3. 執行緒分析器。Microsoft.VisualStudio.Threading.Analyzers 會抓出 async void、同步等待與被遺忘的工作。CA2007 要求 Core、Platform 與驅動程式使用 ConfigureAwait(false)。兩者都是建置錯誤。
  4. 邊界測試。1.3 組件與相依性中的相依表，會針對編譯後的組件進行檢查。驅動程式不得呼叫 Loc。
  5. 棘輪只降不升。檢視與檢視模型中的舊式寫法（async void、Task.Run、.Enabled =、MessageBox.Show、Invoke(）會被計數，尚未啟用可為 Null 參考型別的檔案也一樣。每個檢視模型的建構函式參數數量都有上限。移除程式碼的 pull request 會同時調降基準值。要提高基準值，必須在審查中說明理由。
  6. 容器可以建置。有一個測試在模擬模式下建置容器，並解析主視窗與每個頁面。
  7. 生產路徑變更時比對生產紀錄。請見 4.1 測試中的序列測試。
  8. 日誌檢查。CA2254（常數訊息範本）是建置錯誤。原始碼掃描遇到空的 catch 區塊與 throw ex; 時會失敗。請見 3.5 與 3.6。
  9. 數字放在測試中，而不是文件中。文件描述規則與決策。會變動的計數放在棘輪測試中。

每次推送都會建置方案，並在模擬環境中執行 Hardware 類別以外的所有測試。

4.3維護與版本管理

  • 套件。一旦有第二台機台使用，Platform 與驅動程式就移到自己的儲存庫，成為內部 NuGet 來源上具版本的套件。每台機台固定自己使用的版本。在同一主版本內，合約變更只能是新增。
  • 專案檔。所有專案都是 SDK 樣式。Directory.Build.props 保存共用屬性。中央套件管理（Directory.Packages.props）讓每個組件使用相同的套件版本。
  • 執行環境。只要廠商 SDK 仍有需要，主程式與驅動程式就維持在 .NET Framework（4.7.2 或更新版本）。與 UI 無關的組件（Platform、Core、Presentation）以 .NET Standard 2.0 為目標，因此在 SDK 允許時，不需修改即可移到 .NET 8。
  • 語言。Directory.Build.props 為每個組件把 LangVersion 設為 12、Nullable 設為 enable。原始碼產生器 PolySharp 會補上 .NET Framework 缺少的屬性（attribute），以支援 record、init、required、索引與範圍，以及可為 Null 的註釋。
    • 可自由使用：record、init、required 成員、switch 運算式與模式比對、檔案範圍命名空間、全域 using、主要建構函式、集合運算式。
    • .NET Framework 上無法使用（需要執行階段支援）：預設介面成員、靜態抽象介面成員、共變數傳回型別。
    • 可為 Null 的警告在 Platform 與新組件中視為錯誤。既有程式碼在被修改時逐檔開啟（#nullable enable），並由一個棘輪（G5）計算尚未開啟的檔案數。
    • 調升固定的語言版本至 C# 13 或 14 只需修改一行，待所有開發人員與建置伺服器都使用支援的工具鏈後再進行。
  • 決策紀錄。每項架構決策都在儲存庫中有一份簡短的 ADR（docs/adr/NNNN-title.md），記錄其理由與替代方案。本文只陳述結果。
  • 每個組件一份 README，說明其用途、可以參考什麼，以及如何測試。
  • 變更紀律。每次提交都必須能建置、通過所有測試，並能在模擬模式下啟動。行為變更放在獨立的提交中，並列出以便在機台上驗證。重構提交不改變行為。

    執行 Hardware 合約測試，然後執行裝機調試檢查表。

5.2WPF 遷移路徑

導入 WPF 時，檢視層以下的一切都不會改變。遷移逐頁進行，每一步完成後應用程式都可以出貨。

  1. 每個頁面都有檢視模型前提條件

    WinForms 檢視繫結到這些檢視模型。之後的所有步驟都依賴這一點。

  2. 新增 LTT.UI.Wpf一個組件

    JogPad 與裝置面板的 WPF 版本，以及與 LocUi 對應的字型輔助方法（每種語言的字型家族來自 languages.tsv）。事件匯流排與命令在 WPF 中已可運作。

  3. 在 WinForms 視窗中裝載 WPF 頁面ElementHost，一次一頁

    每個遷移的頁面都在同一個檢視模型之上建立 XAML 檢視。操作員自始至終看到的都是同一個應用程式。

  4. 把主視窗切換為 WPF其餘部分使用 WindowsFormsHost

    尚未遷移的頁面，以及操作員使用的任何廠商畫面，都裝載在 WindowsFormsHost 中。位於擁有者執行緒上的控制項不受影響，因為它們從不顯示。

  5. .NET 8（另行決定）選用

    與 UI 無關的組件已經是 .NET Standard 2.0。請先在 .NET 8 x64 上檢查每個廠商 SDK；原生 SDK 與 ActiveX 控制項是主要風險。

已知的 WPF 限制：裝載在 WPF 中的 WinForms 內容永遠繪製在最上層（即「airspace」問題）。請為 AISYS VAlign 等廠商畫面保留獨立區域，其上方不要有 WPF 快顯視窗或覆蓋層。
